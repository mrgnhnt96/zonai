- [ ] **Cut releases as drafts, verify the assets on a clean slate, then promote.** Proposed 2026-08-13 after v0.6.3 shipped broken. The current shape publishes first and verifies second — `cross-build-linux-x64 (released)` runs `needs: release`, and its own comment concedes the trade: *"a regression here means re-cutting a patch, which is the price of the fetch being release-shaped."* That price is too high, and it is avoidable. The verification needs the assets to exist at a URL, not to be **public**: a **draft** release has assets and a download URL, is invisible to `releases/latest`, and can be deleted without anyone having seen it. Two things this fixes beyond the obvious. It makes "the assets are self-contained" a *tested property* rather than an assumption — today's failures were all environmental leakage (a stale artifact from another commit; `apps/zonai/lib/gen/` present locally and absent in CI), and a no-artifacts-in-scope runner is what makes that class impossible to miss. And it removes the VERSION/website race in the entry below, because the site can key off published releases while a draft is invisible to it. Note the promotion step must keep `--prerelease` handling straight for the same reason `native-libs.yml` does: `/releases/latest` returns the newest non-prerelease release of any kind.

- [ ] **The release version has two owners that contradict each other, and the gap between them is publicly visible.** Hit for real on 2026-08-13 while cutting 0.6.3. `deploy-website.yml` fires on any push touching `VERSION`, runs `sync_version.dart`, and rebuilds the public site with install and download URLs at `releases/download/v$VERSION/...`. Its own comment says regenerating is what *prevents* advertising "a version that was never released" — and that holds only under its stated assumption, "the release workflow commits it", i.e. VERSION lands on `main` **after** the tag exists. But `tool/ci/resolve_release_version.sh` uses VERSION only when it is *greater* than the latest release tag and otherwise bumps the **minor**, so cutting a *patch* requires bumping VERSION by hand and pushing it **before** the release. The two rules cannot both be satisfied: pinning a patch necessarily publishes a website advertising a tag that does not exist yet, for as long as the release takes — or forever, if it fails, which is exactly what happened (release run `31746052351` died before tagging and left zonai.dev's `curl` install command pointing at a 404). **Plan, decided 2026-08-13 after it broke twice in one evening** (once when 0.6.3 was bumped before the tag existed, again when 0.6.3 was deleted and the site kept advertising it):

**The website must derive its version from a release that exists, never from `VERSION`.** `VERSION` states an *intent to release*; the website makes a *promise to download*. Those are different facts and only one of them is safe to publish. Three parts, in order of importance:

1. **Point `apps/website/tool/sync_version.dart` at the newest published release instead of at `VERSION`.** `tool/ci/latest_cli_release_tag.sh` already returns exactly the right thing — newest non-draft, non-prerelease, `^v[0-9]+\.[0-9]+\.[0-9]+$` — and is already trusted by `resolve_release_version.sh`. This single change inverts the failure mode from "site is broken" to "site lags by one release", which is survivable and self-correcting.
2. **Drop `VERSION` from `deploy-website.yml`'s trigger paths.** With (1) done it is not merely unnecessary, it is misleading: a VERSION-only push would rebuild the site to produce byte-identical output. The release workflow's `workflow_call` already republishes the site after a release, which is the moment the displayed version legitimately changes.
3. **Keep the prerelease filter in whatever queries releases.** `native-libs-cache` is a real release on this repo and `/releases/latest` would return it if it were not marked prerelease — the filter in `latest_cli_release_tag.sh` is what makes step 1 safe, and anything reimplementing it must keep it.

If the draft-release proposal above lands, this gets easier still: a draft is invisible to that query by construction, so the site cannot see a release until it is promoted, without anything having to coordinate.

- [ ] Investigate an optional `attach` capability on tables — or on "table groups" — letting a table declare that it lives in its own database file rather than in `zonai.sqlite`, joined back through SQLite's `ATTACH` so it stays queryable through the normal `/db`/`get`/`mutate` surface. Motivating case (wholesale-command-station, 2026-08-13): `_log` grew to 4,164,727 rows and filled a 1GB production volume to 100%, and every recovery path zonai ships — `DELETE`, `VACUUM`, `wal_checkpoint` — needs a write the full disk is denying. A separate file changes what is possible rather than just what is tidy: `unlink` is the only reclamation primitive that does not require the resource being reclaimed, `VACUUM` takes its exclusive lock on the disposable data instead of on the application's own tables, and `PRAGMA max_page_count` becomes usable at all (it caps a *file*, so on a shared database the ceiling is hit by whichever write arrives first — application inserts included). **Update 2026-08-13: `_log` and `_rate_limit` are both split** (`zonai_log.sqlite`, `zonai_rate_limit.sqlite`), and the mechanism generalized as far as a `_disposableTableSchemas` map in `zonai_db.dart` — adding a table is now that entry plus its indexes. What remains of this entry is the *declarative* half: letting a schema say so itself, so retention, capping and vacuum policy are derived rather than listed. Two things learned doing it that any design here inherits: an attached database inherits nothing (not the journal mode, which defaults to `delete` beside a WAL `main`, and not the second connection), and the drop-before-create ordering is load-bearing because `main` wins unqualified name resolution. Worth designing around the idea that some tables are *disposable* — high-churn, bounded-retention, reconstructible-or-not-worth-reconstructing — and that the schema is the right place to say so, since that one declaration is what would let retention, capping, vacuum policy and crash recovery all be derived rather than hand-wired per table. Candidates beyond `_log`: `_rate_limit`, `_auth_challenges`, `_cron_jobs`. Deliberately not scoped further here; flagged as a real need, not designed.
- [ ] Add a "view" table concept — a read-only, joined/projected shape defined once in schema, queryable through the normal `/db`/`get`/`mutate` surface like a real table. Motivating case (override_canvas, 2026-07-25): `ListBody`/`/db/list` has no column-projection support today — listing rows always returns every column, including large ones (e.g. a `recordings` table storing a full base64 payload inline) even when a UI only needs a handful of lightweight fields for a list view. A generic `fields:`/`select:` param on `ListBody` would fix that specific case, but a proper "view" — a named, reusable projection (and eventually a join across tables) defined in schema once — is the more durable fix: it'd also cover "denormalize this join for the dashboard" cases without every caller re-specifying the same field list, and gives `raindrop` a real join story to build toward (see "Add support for one to many relationships" above — a view is a natural place to expose the joined shape once relationships exist). Deliberately not scoped further here; flagged as a real, recurring need, not designed.

Today both `POST /auth/sign-up` and `POST /auth/sign-in` resolve through one `_authenticate` (`parts/auth/auth.dart`), which branches only on whether an auth record exists — so signing up an existing email signs it in, and the payload's intent is never read. Small to build: `SignUpAuthBody`/`SignInAuthBody` are already distinct types reaching distinct controller methods (`auth_password_body.dart:480,517`) and only collapse to one `PasswordAuthPayload` before the decision — thread the intent through and branch on it rather than on existence alone.
