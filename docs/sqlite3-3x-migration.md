# Migrating to sqlite3 3.x

zonai is pinned to `sqlite3: ">=2.4.0 <3.0.0"`. This document records why, what
was measured, and what a real 3.x migration would have to do.

**Do not lift the pin without reading this.** The failure mode is silent.

## Why the pin exists

`ResqliteDelegate.open` opens the *same database file* twice: once through
resqlite (the writer, a custom sqlite3mc build) and once through
`package:sqlite3` (the read connection). Two independently-built SQLite
libraries touching one file in one process is a documented, 100%-reproducible
segfault — resqlite's build sets different `SQLITE_*` flags (`THREADSAFE=2`,
various `OMIT`/`ENABLE`), so the struct layouts differ and
`sqlite3LeaveMutexAndCloseZombie` corrupts on the first query.

sqlite3 2.x avoids this with an explicit handle:

```dart
open.overrideForAll(() => rs.installedNativeLibrary);
```

Both connections then run the exact same code. sqlite3 3.0.0 removed
`DynamicLibrary` loading, and with it `overrideForAll`.

## What does not work

### `user_defines: sqlite3: source: process`

This is the package's own documented replacement, and it reads like an
equivalent — the enum's doc comment says "lookup a sqlite3 library that has
already been loaded into the process". It is not equivalent.

`source: process` resolves to `LookupInProcess()`, i.e. `dlsym(RTLD_DEFAULT)`,
which binds to whichever `sqlite3_*` symbols are in the process **first**, in
load order. It guarantees *a* SQLite. It does not guarantee *ours*.

Measured on macOS (2026-08-12):

```
$ DYLD_PRINT_LIBRARIES=1 ./probe
dyld[26520]: <2197AD4A-...> /usr/lib/libsqlite3.dylib     # image #103
```

`/usr/lib/libsqlite3.dylib` is pulled in transitively by the system frameworks
the Dart runtime links, **before `main()` runs**. resqlite's `dlopen` happens
later and can never outrank it. Result:

| library | version | sourceid |
| --- | --- | --- |
| what `package:sqlite3` bound to | 3.51.0 | `2025-06-12 …dcaapl` (Apple's) |
| resqlite's `libresqlite.dylib` | 3.51.3 | `2026-03-13 737ae4a3…` |

A second probe that loaded **nothing at all** — no `dlopen`, no
`DynamicLibrary.open` — still ran `sqlite3.openInMemory()` and `CREATE TABLE`
successfully, proving `rs.install()` contributes nothing to the binding.

This does not fail loudly. resqlite exports the full standard sqlite3 C API, so
every symbol resolves, `dart analyze` is clean, and the test suites stay green —
they exercise `package:sqlite3` alone and never open a real file through both
libraries. Only the segfault tells you.

### Vendoring sqlite3's `lib/` with `@ffi.DefaultAsset` stripped

Motivation: `dart compile exe` refuses outright when any dependency declares a
build hook (`'dart compile' does not support build hooks, use 'dart build'
instead. Packages with build hooks: sqlite3.`), and sqlite3 3.x has one. The
idea was to vendor `lib/`, drop `lib/src/hook/`, and strip the
`@ffi.DefaultAsset` annotation so `@Native` falls back to process lookup — the
same trick `libs/resqlite` uses.

The mechanics all work:

- `dart analyze` clean; nothing outside `src/hook/` imports
  `hooks`/`code_assets`/`native_toolchain_c`/`crypto`, so vendoring drops those
  deps too.
- `dart compile exe` succeeds — the build-hook error is gone.
- `@Native` without `@DefaultAsset` really does fall back to process lookup.

But "process lookup" is the same `dlsym(RTLD_DEFAULT)` as above, so it lands in
Apple's SQLite for exactly the same reason. **The vendoring is not the problem;
process lookup is.** Any strategy that ends in process lookup fails on macOS.

## What would work (option 2)

Vendor sqlite3 3.x **and** rewrite its generated bindings to look symbols up
through an explicit `DynamicLibrary` handle — `rs.installedNativeLibrary` —
instead of `@Native`. That restores the 2.x guarantee without a build hook.

Feasibility read of `sqlite3-3.5.1/lib/src/ffi/libsqlite3.g.dart` (2205 lines):

- **92** `@ffi.Native<...>()` functions, **all** with implicit symbol names —
  zero explicit `symbol:` or `assetId:` arguments to special-case.
- **Zero** `@Native` globals; every annotation is on a function.
- `addresses` is a single `const _SymbolAddresses()` used in only 5 places, all
  `NativeFinalizer`/`sqlite3_free` pointers (`bindings.dart:36,37,40,43,168,652`
  and `api.dart:73`). Each becomes
  `lib.lookup<NativeFunction<...>>('name')`.
- `const addresses` and `const ffiBindings` would have to become lazy `final`s,
  since the handle is not known at compile time.

The file is generated by `ffigen` and very regular, so the transform belongs in
a vendor tool (extend the pattern in
`libs/zonai_schema/tool/generate_raindrop_vendor.dart`) rather than a one-time
hand edit. The cost is that it forks a generated file: any change to ffigen's
output shape breaks the transform, loudly.

There is no injection point that avoids this. `ffiBindings` is a `const`
singleton over the `@Native` top-levels, and `lib/unstable/ffi_bindings.dart`
merely re-exports the generated file — sqlite3 3.x exposes no way to supply your
own `DynamicLibrary`.

## Option 3, for completeness

Drop `package:sqlite3` from the runtime read path entirely and let resqlite
serve reads too. One SQLite in the process by construction, and the whole class
of problem disappears. The largest change of the three.

## Reproducing the measurement

```dart no-analyze
// no-analyze: the import is a placeholder for whatever package the vendored
// copy lands in, so this cannot resolve as written.
//
// Compile with `dart compile exe` against a vendored, DefaultAsset-stripped
// sqlite3. Load nothing. If this prints a version, process lookup already
// found a SQLite that is not ours.
import 'package:<vendored>/sqlite3.dart';

void main() {
  print(sqlite3.version);          // 3.51.0 ... aapl  -> Apple's
  sqlite3.openInMemory().dispose();
}
```

Compare against `resqlite`'s own library:

```bash
python3 -c "
import ctypes
l = ctypes.CDLL('apps/zonai/.dart_tool/lib/libresqlite.dylib')
l.sqlite3_sourceid.restype = ctypes.c_char_p
print(l.sqlite3_sourceid())
"
```

If the two sourceids differ, `package:sqlite3` is not running resqlite's SQLite.
